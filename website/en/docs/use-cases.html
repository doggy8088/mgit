Why mgit exists

Once a project grows, repositories end up scattered across one working directory: the app, a shared package, examples, deploy scripts, a docs site — each its own repository, referring to each other by relative path, with no git submodule wiring them together. mgit was written for exactly that: one command to manage the git repositories under several child folders.

A typical day

  • mgit --list: see which repositories under this directory will be touched.
  • mgit: every repository's status at once (no arguments = git status -s).
  • mgit pull: update them all in one run; failures are listed in the summary.
  • mgit log --oneline -n 1: the latest commit of each repository.
  • mgit --fail-fast pull: stop at the first conflict instead of ploughing on.

How it differs from submodules and from a monorepo

ApproachWho owns the versionDoes it touch the repositoriesWhen it fits
git submoduleThe parent records each submodule's commit; updating means committing the parentNeeds .gitmodules in the parent and a remote in each childPinned versions and reproducible builds
One monorepoOne repository, one historyEverything moves in: history, permissions, CI and release rhythm change togetherThe team and its process are already unified
mgitNo relationship at all; every repository stays independentNone: mgit puts no files inside a repositoryRepositories scattered in one working directory that must move together

When it is the wrong tool

  • You need pinned dependency versions and reproducible builds → use git submodule or vendoring.
  • You need one CI, one release, one permission model → that is a monorepo problem; merge the repositories first.
  • mgit changes nothing inside the repositories and resolves no version relationship: it only sends the same command to every child directory.
