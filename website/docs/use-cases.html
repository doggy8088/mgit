為什麼會有 mgit

專案一多，repo 就會散在同一個工作目錄底下：應用程式、共用套件、範例、部署腳本、文件站各自是一個 repo，彼此要用相對路徑互相參考，卻沒有用 git submodule 綁在一起。mgit 就是為了這個情境寫的：一個指令，管理多個子資料夾下的 git repo。

典型的一天

  • mgit --list：先看清楚這個目錄下會被動到哪些 repo。
  • mgit：每個 repo 的狀態一次看完（不帶參數＝git status -s）。
  • mgit pull：一次把全部更新，失敗的會列在摘要裡。
  • mgit log --oneline -n 1：一次看每個 repo 的最新一筆。
  • mgit --fail-fast pull：有衝突就停下來處理，不要一路錯到底。

與 submodule、monorepo 的差別

做法版本由誰管要動到 repo 內容嗎什麼時候適合
git submodule父專案記錄每個子模組的 commit；要更新就得 commit 父專案要在父專案放 .gitmodules，子 repo 也要有 remote需要精確鎖定版本、可重現的建置
單一 monorepo一個 repo、一條歷史要把所有東西搬進去（歷史、權限、CI、發佈節奏一起改）團隊與流程已經統一
mgit沒有關係，每個 repo 各自獨立不用：mgit 不會在 repo 裡放任何檔案repo 散在一個工作目錄、需要一起操作

什麼時候不適合

  • 需要精確鎖定每個相依的版本、建置要可重現 → 用 git submodule 或 vendoring。
  • 需要單一的 CI、單一的發佈與權限 → 那其實是 monorepo 的問題，先把 repo 合併。
  • mgit 不改變任何 repo 的內容，也不解決版本關係：它只是把同一個指令送到每個子目錄。
