Versions, releases and npm

Differences from 1.0, the tag-driven release flow and the npm package

Differences from 1.0 (the shell version)

The old version was two scripts, mgit (Bash) and mgit.ps1 (PowerShell); both are archived under archive/. The rule for the new version: keep the default behaviour and the output format, fix the real defects.

Item1.0.02.x
FormA Bash script and a PowerShell script, maintained separatelyOne Rust binary, one test suite, every platform
Default commandgit status -sUnchanged
Output format80 =, 📂 Folder: … │ Branch: …Unchanged, plus an ASCII mode
Nothing foundCompletely silent, exit code 0Warns and exits with 1 (--allow-empty restores the old behaviour)
Exit codesAlways 0 in multi repository modeAggregated: the first failing exit code becomes the result
OptionsNone, every argument went to gitAdds --list, --depth, --quiet, --color, --ascii, --summary, --fail-fast, --allow-empty
ColorAlways emitted ANSI escapesDecided from the terminal's capabilities, honoring NO_COLOR / CLICOLOR_FORCE
Website and installerspublic/ plus the scripts themselvesThe installers download and verify the published release

Versions and releases

The version lives in Cargo.toml and follows SemVer; Cargo.toml, Cargo.lock, npm/package.json, CHANGELOG.md and the git tag must all agree.

# 2.0.2 → 2.0.3, one command, three filesscripts/bump-version.sh patch
# the tag starts the releasegit tag -a v2.0.3 -m "mgit 2.0.3" && git push origin HEAD v2.0.3
  • Every version must first add a ## [X.Y.Z] - YYYY-MM-DD section to CHANGELOG.md; that section becomes the GitHub Release notes.
  • The release workflow verifies the version, runs the full test suite, builds all eight targets with checksums, and publishes the GitHub Release with SHA256SUMS.txt.
  • The npm workflow then publishes @willh/mgit with trusted publishing, no token involved.
After a release

The installers run on three platforms against the published release as a final check, and the npm package ships with a provenance signature.
